# Decisions

Append-only. These are not preferences: they are decisions made for specific
reasons, and changing them requires going back to those reasons. New rows at
the bottom; a superseded decision gets a new row naming the old one, never an
edit.

| # | Date | Who | Decision: why, alternatives rejected, proof, files |
|---|------|-----|------------------------------------------------------|
| 1 | 2026-11-25 | Amit + Claude | **Adopted the devlog system (progress log, decision log, tickets, release registry, session-wrap discipline).** Why: decisions and observations were living only in conversations and commit messages, invisible to future sessions. Files: `docs/PROGRESS.md`, `docs/DECISIONS.md`, `docs/tickets/`, `docs/RELEASES.md`, `CLAUDE.md`. |
| 2 | 2026-11-25 | Claude, reported to Amit | **Version policy: `pyproject.toml` is the canonical carrier, mirrored in `claude_cfg/__init__.py` and `.claude-plugin/plugin.json`; SemVer; carriers moved to 0.3.0 for the plugin work without cutting a release.** Why: a plugin manifest needs a version, and the docs say that when it is set it must be bumped for users to get an update; the change adds features and a new on-disk format, so a minor bump under 0.x. A test (`tests/test_plugin_manifest.py`) fails if the plugin and package versions differ. Pushing a `v*.*.*` tag publishes to PyPI through `.github/workflows/release.yml`, so tagging is a release, not a label. Rejected: leaving the manifest version out (updates would then track every commit). Files: `pyproject.toml`, `claude_cfg/__init__.py`, `.claude-plugin/plugin.json`, `docs/RELEASES.md`. |
| 3 | 2026-11-25 | Amit ("do all") + Claude | **Snapshots are protected by passphrase encryption of the whole zip, with `cryptography` as a required dependency.** Why: `settings.json` can hold keys and 0.2.0 shipped it in plain zips; encrypting the whole object covers every backend and every file. scrypt (N=2^15, r=8, p=1) and AES-256-GCM, header as associated data, magic `CCFGENC2`. A plain snapshot is refused when local encryption is on unless `--allow-plain` is passed, because a reviewer restored a planted plain zip with no passphrase. Rejected: redacting known secret fields on push (misses unknown fields and breaks restore), and only warning (protects nothing); making `cryptography` an extra (encryption would be off on a plain install). Proof: all 63 truncations and 63 bit flips of an envelope were rejected in review. Files: `claude_cfg/encryption.py`, `passphrase.py`, `passphrase_verifier.py`, `snapshot_store.py`. |
| 4 | 2026-11-25 | Claude | **`pull` stays an overlay by default; removing files is opt-in through `--exact`, behind a confirmation, and only inside roots that both the snapshot and this machine's config track.** Why: deleting by default would surprise 0.2 users, and a snapshot's own `tracked` list is attacker-influenced input: in review a manifest listing `history.jsonl` and `file-history` got them planned for deletion. Excluded paths are never deleted. Rejected: exact as the default. Files: `claude_cfg/restore_plan.py`, `pull_manager.py`, `exclusion_filter.py`. |
| 5 | 2026-11-25 | Claude | **The objects under `snapshots/` are the source of truth and `index.json` is a cache; a pusher that sees any other object with its id yields and retries under a new id.** Why: 0.2.0 read, appended and rewrote `index.json` with no lock, so two machines could drop a snapshot or reuse an id. A first version of the rule (lower key wins) had a window where a late rival concluded it had won; yield-always closed it. Proof: 150 threaded rounds of three pushers, no duplicate, lost or orphaned snapshot. A lagging sync folder can still show two objects with one id; that is reported and `pull --key` selects one. Files: `claude_cfg/snapshot_store.py`, `snapshot_index.py`, `snapshot_keys.py`. |
| 6 | 2026-11-25 | Claude | **MCP servers are read from `.claude.json` and written only through `claude mcp add-json <name> - --scope user`, with the definition on stdin. The tool never writes `.claude.json`.** Why: that file mixes MCP config with account and per-project state, Claude Code rewrites it while running, and hand-editing it is not documented; definitions hold tokens, and command-line arguments are visible to other local processes. Consequence: restore needs the `claude` CLI at 2.1.327 or later and a terminal outside a Claude Code session, and is skipped with a report otherwise. Rejected: writing the JSON key directly (corruption and clobber risk); not syncing MCP at all. Opt-in, default off. Files: `claude_cfg/mcp_server_sync.py`, `mcp_cli_preflight.py`, `mcp_server_capture.py`. |
| 7 | 2026-11-25 | Claude | **Session notices are printed as a `systemMessage` JSON line, never as plain hook output.** Why: the docs say a SessionStart hook's plain stdout goes into Claude's context. Proof: in a test session the model repeated a code word from plain stdout and answered NONE for the same text in `systemMessage`; repeated in three sessions with the real plugin. Files: `claude_cfg/session_hook_manager.py`, `session_start_notice.py`. |
| 8 | 2026-11-25 | Claude | **On a case-insensitive disk, snapshot names match files by folded name; on a case-sensitive disk only the exact name matches. The exclusion filter folds on every platform.** Why: on macOS an exact pull wrote `skills/foo/SKILL.md` into `skills/Foo/` and then deleted it as a local extra, and `.Credentials.json` overwrote the credentials file; folding everywhere then broke Linux, where `README.md` and `Readme.md` are two files. The filter over-excludes on purpose, since excluding too much is the safe direction. The disk is probed with a temp file. Files: `claude_cfg/path_matching.py`, `path_identity.py`, `exclusion_filter.py`. |
| 9 | 2026-11-25 | Amit | **The plugin is named `config-history`.** Why: plugin names starting with `claude-`, `anthropic-`, `anthropics-` or `cc-plugin-` are reserved, so `claude-cfg` cannot be used; the name states what most users want it for. The PyPI package and the repo keep the name `claude-cfg` for now. Rejected: `cfg-sync` (stresses syncing over history), `settings-snapshots`. Files: `.claude-plugin/plugin.json`, `.claude-plugin/marketplace.json`. |
| 10 | 2026-11-25 | Amit (behavior) + Claude (defaults) | **When config changed, the plugin saves a local version automatically at session start and end and shows one line. Auto-save is on for the default local history and off for a backend set up through `init`; the newest 50 automatic versions are kept and a hand-saved version is never deleted.** Why: an alert arrives after the change, when the earlier state may already be gone; "go back" is a local history problem that needs no backend. Pushing to a shared remote on every change is a decision the user should make, so a configured backend gets a "changes not saved" notice instead. Rejected: alert only; live in-session alerts through `ConfigChange` (its user-visible output is not documented, and it misses `CLAUDE.md`, keybindings and plugin installs). Files: `claude_cfg/autosave_manager.py`, `autosave_setup.py`, `snapshot_retention.py`, `default_history.py`. |
| 11 | 2026-11-25 | Amit | **The plugin installs itself: on first start it builds a private virtual environment in the plugin data folder with the Python already on the machine, and the tool supports Python 3.9.** Why: a plugin that still needs a separate `pip install` loses its point; the data folder is the documented place for environments and survives updates; macOS ships 3.9.6 at `/usr/bin/python3`. The install runs detached so session start is not blocked, builds an update beside the working environment and swaps on success, and backs off after a failure. Versions are pinned in `scripts/plugin-constraints.txt`. Rejected: a thin wrapper that leaves `pip install` to the user. Proof: `523 passed` on 3.9.6; first install took about 9 seconds. Files: `scripts/config_history_*.py`, `scripts/config-history-hook.sh`, `bin/config-history`. |
| 12 | 2026-11-25 | Amit | **Publish through this repo as its own marketplace first.** Why: no review gate, and nothing is wasted if a later directory submission is rejected. Anthropic's directory needs a paid plan and passes a review whose checklist has not been read yet; a plugin whose hooks read all of `~/.claude` should expect scrutiny. See open question 1. Files: `.claude-plugin/marketplace.json`. |
| 13 | 2026-11-25 | Claude | **Under `plugins/` only `installed_plugins.json` and `known_marketplaces.json` are captured, and a change to `known_marketplaces.json` alone never triggers an automatic save.** Why: tracking all of `plugins/` captured the plugin's own environment (1,462 of 1,463 files, 8.8 MB per version, about 440 MB at 50 versions) and cache files Claude Code rewrites every session, which would have produced a version and a notice almost every session. Rejected: excluding `plugins/data/` alone (other cache files would still churn). Files: `claude_cfg/exclusion_filter.py`, `volatile_paths.py`. |
| 14 | 2026-11-25 | Claude | **Plugin skills pre-approve read-only commands only; a real restore and an undo go through Claude Code's permission prompt.** Why: the first version pre-approved `config-history restore *`, which covers `--exact --yes`, so the skill's confirmation was only prompt text. Pre-approving just the dry run makes the permission prompt the confirmation. Files: `skills/restore/SKILL.md`, `skills/undo/SKILL.md`. |

## Open questions

Intentionally deferred decisions. Each states the question and the trigger for
revisiting it. When resolved, it becomes a decision row and is struck from
this list with a pointer to that row.

1. **Submit the plugin to Anthropic's directory?** Deferred because the
   submission checklist (`claude.com/docs/plugins/pre-submission-checklist`)
   has not been read and the plugin has not been published or tried
   interactively. Revisit after the first release from the own marketplace;
   read the checklist first and report whether the plugin fits it. The icon
   decision matters here, since the first submitted icon is permanent
   (`docs/tickets/plugin-has-no-icon.md`).
2. **Should the PyPI package and the repo keep the name `claude-cfg`?** Only
   the plugin name is constrained today (row 9). Revisit if a directory
   submission or a trademark concern makes the difference between the two names
   a problem.
3. **Should auto-save be offered for a configured sync backend by default?**
   Row 10 leaves it off. Revisit when a user with a remote backend asks for it,
   or when there is evidence that the "changes not saved" notice is ignored.
